# 界面与设备工作流及触发场景

## 缺少可渲染素材

缺少可渲染素材时，不把任务无限推迟，也不假装已经产出图片或动画。先提供 2–3 个具名文字候选，逐个写明布局/形态/动效重点、只允许变化的范围、必须保持不变的交互与产品语义，以及后续渲染所需素材。具名文字候选不等于已渲染预览；用户选定方向后才制作隔离预览，预览获批后才允许集成。

若用户要求现在查看候选且项目保持只读，在回复中附每个方向的自包含 SVG 或 HTML 预览代码/可直接查看的数据内容，不写入项目。预览使用明确尺寸、页面状态和占位素材，并声明它不证明正式源码集成、真实动效、交互或设备表现；只有用户点名候选并批准对应渲染预览后，才可申请正式集成范围。

## 对比与适配检查

- 在相同页面状态、视口、字体缩放和素材条件下比较参考与实现。
- 先看结构与层级，再看尺寸/间距、形态、色彩、字体、素材和动画；不能只凭“观感接近”。
- 边界矩阵至少覆盖最窄屏、最长文案、最大数字、安全区、键盘遮挡、空/加载/错误和重复操作反馈。
- 异步空态区分 unresolved、resolved-empty、resolved-with-data；可重入回调用 attempt ID 阻止旧操作写入新状态。
- 复杂首屏记录顶部、标题/tab、核心内容、主操作、底部导航和安全区的数值高度预算，局部修改后复算整页。
- 设备策略按需要组合 system、model、brand、safe-area、viewport 与能力探测，不只依赖单一平台字符串。
- 手势冲突矩阵记录手势、区域、竞争对象、预期优先级、实际结果、失败路径和验证设备。
- 只有真实设备证据才能使用 `device-verified`；截图只能证明截图所示状态和时刻。

## 代表场景

### 场景 1：正常场景——按参考图先做视觉预览

用户给出明确参考并要求先看效果。应在隔离预览中复现布局、形态和关键状态，列出差异；在用户确认前不集成到正式页面。

### 场景 2：正常场景——已确认方案的响应式集成

视觉方向已经批准。只修改授权界面文件，并用最窄屏、最长文案、最大数字、安全区和键盘场景检查布局；报告本地结果但不冒充真机。

### 场景 3：边界场景——滚动与横滑手势竞争

页面同时存在纵向滚动、横向卡片和返回手势。建立手势冲突矩阵，明确触发区域、方向阈值和失败恢复；无设备证据时保留待真机验证。

### 场景 4：失败场景——参考目标互相冲突

原型、截图和当前用户说明对顶部结构不同。列出冲突及受影响区域，推荐权威来源并停在确认点，不能自行拼成第四种设计。

### 场景 5：不应触发——纯数据接口错误

界面布局正常，但接口返回错误码导致无数据。应进入调试或架构流程，不以占位视觉掩盖接口失败。

### 场景 6：边界场景——旧异步回调晚到

用户连续触发录音、上传或短时提示。每次操作生成 attempt ID，旧回调在写状态或停止资源前必须校验 ID；不匹配时只能清理自身，不能覆盖当前操作。

## 共享交互全入口矩阵

改公共菜单/弹层前，按实际引用列正常详情、历史/删除态、顶部等入口，核打开/关闭、互斥、焦点归还、尺寸及破坏性确认，再组合语言、主题、窄屏。共享组件/样式不证明调用处事件和生命周期一致，全部入口未核不称全局统一。动作菜单可按确认规则轻便关闭，含输入表单保留草稿/确认保护，不套用会丢输入的自动消失。触控、鼠标、键盘按目标能力适配，不强制悬停或搬固定尺寸/延时。


## 表单失败后的可见纠错闭环

有阻断校验且错项可能屏外、被键盘或固定底栏遮挡时，从用户点击提交的位置核真实可见区域：能直接读到可行动的说明，或通过一次明确定位找到对应字段；节点树有文字、颜色变化或一闪即逝不证明用户能纠错。脚本断言可核错误文本与定位参数写入，定位后的可见区命中须有同口径布局测量或受控渲染回执，真机表现另验；不从参数更新直接推断实际落点或可读性，复验预期须对应所需证据层级。按已确认交互和平台能力处理滚动/焦点，不统一要求失焦报错、自动跳转或新增弹窗；短表单已可用沿原交互，无表单场景不增加流程。

失败保留其他合法输入与可恢复草稿；当前值改正后清除对应的旧校验错误，过期回包不覆盖新编辑。服务/业务失败按其独立条件处理，不以输入合法消除真实失败。校验失败不触发被本轮校验阻断的业务写入。提交归属及确认复用先核项目已确认的写入合同与实际确认标识，再沿[运行时合同](runtime-state-and-layout-contracts.md#同轮保存的多入口收尾)处理确属同一确认的重复触发；内容相同、再次点击或同一按钮，不自行证明是同一确认。通用指导不是项目已有业务事实，缺少确认归属或复用规则时记为待核，不能据此把既有合法写入判成违约、补造已确认的去重合同或阻断获准的后续独立业务。

将最小修复重新代入未改正与真正改正的输入：仍非法时保持当前可行动说明，真正改正后才清对应校验错误，不能在任意输入事件中无条件清空。修复建议与复验预期须一致，不能前文建议一输入就清错，后文却要求非法输入保留提示。待核现象在摘要、缺口清单、建议和预期中保持同一证据等级；若原稿先误列为已确认缺陷，纠正时同步改掉原结论，不能仅在后文补一句待核而留下矛盾。已确定的授权范围不重新变成可选解释；授权不足的改动明确列待批，待批效果不写成本批最小修复必过的预期。

执行者先备好匿名数据，在约定对话给普通入口、可复制样例和最短预期步骤；样例不收窄产品值域，另核样例外合法值和真正越界值，产品保留正常字段帮助。验证同时核非法提交、改正后清错/草稿保留及合法普通提交无额外确认、跳转或重复写入，记录找错与重填负担，不凭简短步骤宣称效率提高。

保留失败提交时的视口和改正后状态，分列静态、受控/开发者工具与代表真机的键盘、滚动、焦点及结果；源码/合成几何不证明真机可见，缺设备证据保持unknown。装置点击前超时或临时数据在断言前清理时，记最后送达产品的动作及未执行/证据不足，先修装置、留证再清理，只补失败/未执行段，不把装置故障判作产品失败。证据质量沿[可采信性规则](../../mini-program-verification-skill/references/evidence-admissibility.md)。

## 状态口径

- `proposed`：仅有预览/方案。
- `proposal-approved`：用户明确确认当前视觉方案。
- `implemented`：已正式集成源码。
- `locally-verified`：本地或模拟器检查有结果。
- `device-verified`：真实设备、机型、步骤和证据完整。
- `accepted`：用户正式验收；不能由预览点赞或自动化检查推导。
