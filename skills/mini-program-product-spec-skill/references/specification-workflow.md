# 产品规格工作流与触发场景

## 质量检查

- 每个功能都能回到一个目标用户和核心问题。
- 主流程能闭合，异常流程不会偷偷引入新业务规则。
- 页面职责与状态矩阵一致，同一事实没有多个未说明的状态源。
- 云端权威状态不会由本地缓存缺失推断；首次流程只在权威源确认不存在后出现，重复创建有恢复赢家结果的产品路径。
- 所有假设和未知项都有标签；未来规划不会混入第一版验收。
- 验收标准能由人或测试观察，不依赖“应该”“合理”“友好”等主观判断。

## 代表场景

### 场景 1：正常场景——一句话想法

用户只有“做一个帮助孩子每天练习的打卡小程序”。应先澄清用户、练习闭环和成功条件，再给最小范围、主流程、状态矩阵与验收行为；不自行增加排行、商城或社交。

### 场景 2：正常场景——已有功能新增流程

用户给出当前项目事实和一个新功能。应区分现有事实与新需求，说明哪些页面职责和状态受到影响，并把稳定产品语义交给架构阶段。

### 场景 3：边界场景——信息不全但可安全推进

缺少文案或展示顺序，但不影响核心闭环。可以采用标注为“待确认”的最小假设，继续整理规格，不能把假设写成事实。

### 场景 4：失败场景——关键规则互相冲突

两份材料对是否允许重复领取奖励给出相反规则。应保留冲突、指出受影响流程和验收项，并停止在需要用户决策的位置。

### 场景 5：不应触发——纯代码缺陷

用户提供稳定复现步骤，只要求修复已有按钮的空指针错误，且产品行为没有歧义。应进入调试或实现流程，不需要重新做完整产品规格。

### 场景 6：边界场景——老用户清除本地数据

本地没有记录但云端可能已有权威状态。规格必须先进入 `unresolved` 并读取权威源；只有 `confirmed-absent` 才显示首次创建。若创建返回已存在，读取赢家记录并进入老用户路径，不能把用户困在新手页。

## 交接原则

### 历史意图、恢复与独立目录

仅在已有自动再展示、存量迁移、删除/归档恢复需求时，区分真实动作来源、权威前态与当前入口/筛选；同一“未展示”不能推断用户主动收起或系统排队。缺历史来源沿已批准政策处理，影响存量意图且没有规则时先核影响并给可审阅推荐，不让用户重述已给过的决定，不静默启用自动行为或强加迁移。

恢复去向、父项消失/归属变化/容量冲突的兜底，以及有业务意义的排序/位置来自批准规格。用“恢复到哪里、哪些情况需再确认”解释；不额外发权益/通知、挤走内容或覆盖新状态。没有此需求不增加字段、菜单或恢复区。

权威归属只能证明恢复关系，不能补出缺失的动作来源。恢复交接分别写出来源证据、真实归属/权限及批准的父项/容量兜底；批准政策已明确保留未知项时直接执行，不把未知再交回用户决定。

产品允许独立分类/集合和空项时，分别定义目录存在、入口可选、历史归属、真正删除及权限。移除选项不自动删除实体或清历史，恢复选用也不授予后端权限。规格要求保留历史归属时，修复应只改变目录的可选状态，历史条目和活跃草稿的原归属保持不变；先抄存旧归属再清空当前关系仍不满足保留，不把错误清空持久化当作修复。真删除的迁移/解除关系须已有批准；纯派生筛选、允许空项级联或合法清除义务从其规格，不统一强加保留政策。不为演示增加管理页或深层菜单。

交接只传递目标、事实、流程、状态、验收、未知项和不可改变项。不要把内部推理、未确认候选或视觉偏好包装成架构输入。

验证缺口同时交接下一步和责任：助手先完成可独立执行的受控重建；若结论确需真实生命周期而仍缺证据，列出最小设备操作、版本和通过条件，走到该项再请求配合。不只写“待验证”，不把受控结果升为真机通过。

### 破坏性操作的预览与确认范围

仅在已有获准有限删除/清除/不可逆迁移时，说明完整影响对象、分页/隐藏关联、动作模式、是否可恢复及备份保留边界；业务删除不称安全擦除。沿批准交互给简洁数量与可展开可读清单，查看和取消不发生删除/业务写入，不强制新页、额外弹窗、长名称输入或逐条勾选来替代程序核验。

用户确认绑定对象身份及决定范围/判断的内容和关系版本；相关变化刷新清单并撤销旧确认，再由用户确认，无关集合或全局修订递增不强迫重看。不能由助手代替接受新范围。保存失败保输入、执行失败保原内容、响应未知沿原请求查证，真实保障见[原子执行合同](../../mini-program-architecture-skill/references/cloud-state-and-write-contracts.md)。政策已明确直接执行；仅对真实缺失的删除/备份政策给最小推荐并请求决定。无此功能N/A，不创造删除入口或恢复系统。
