# 架构工作流与触发场景

## 质量检查

- 每个模块都能对应已确认的页面职责或质量目标，没有为技术炫技新增产品能力。
- 关键事实只有一个规范状态源；派生缓存可以被重建，跨页同步有明确触发点。
- 每个写操作都有身份、权限、校验、并发、幂等、失败和可观察结果。
- 数据或接口演进包含兼容期、迁移顺序、回滚条件和恢复路径。
- ADR 同时记录选择和放弃的方案，并把验证映射回产品验收标准。

## 代表场景

### 场景 1：正常场景——从稳定规格设计新项目

规格已包含流程、页面和状态。应给出模块边界、状态源、数据模型、接口与权限、失败策略和 ADR，不直接生成业务代码。

### 场景 2：正常场景——已有项目增加跨页能力

先读取只读事实图和现有模式，再说明受影响模块、依赖方向、数据契约和验证范围；保护工作区已有改动。

### 场景 3：边界场景——局部功能不影响结构

只是固定文案或局部样式调整，现有状态和接口均不变。应说明无需完整架构阶段，保留现有边界并交给实现与验证。

### 场景 4：失败场景——迁移无法安全回滚

方案会覆盖存量数据且没有备份、兼容读取或回滚路径。应停止在架构决策点，列出需要补齐的恢复条件。

### 场景 5：不应触发——产品规则仍冲突

用户尚未决定一次性奖励能否重复领取。应先由产品规格阶段确认语义，不能用数据库唯一键替用户决定产品规则。

## 交接原则

实施交接包含范围、依赖、契约、顺序、门禁、验证和回滚条件。没有实际运行证据时，只称“架构已设计”，不能称功能已实现或验证通过。
