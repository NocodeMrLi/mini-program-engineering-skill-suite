# 问题调试工作流与触发场景

## 证据质量检查

- 复现记录绑定源码/构建、环境、设备、账号/数据状态与时间，不混用历史样本。
- 每个竞争假设都可被某项观察否定；先做只读、低成本、信息增益高的判别实验。
- 根因能同时解释症状、边界和反例；“改完不报错”不等于解释成立。
- 修复前回归测试确实失败，修复后原症状、同类状态和受影响契约通过。
- 真机、云端和平台状态只使用对应层证据；日志中不回显凭证、身份或内部地址。

## 代表场景

### 场景 1：正常场景——异步数据导致数值跳变

页面先显示默认值，再被异步缓存或接口替换。记录渲染时间线，比较默认值、缓存和远端状态，写失败测试覆盖初始化/恢复，再修正唯一状态源或渲染条件；不能只延长加载态。

### 场景 2：正常场景——源码正确但设备仍显示旧行为

核对当前分支、构建时间、开发者工具加载目录和设备版本。若构建版本不一致，将结论停在版本错配；不能重复改源码来追逐旧产物。

### 场景 3：边界场景——外部服务间歇失败

按调用前、传输、服务返回、解析和持久化分段记录错误码、耗时与参数形态，比较成功/失败样本；凭证只核对存在性。证据不足时保留竞争假设，不靠无限重试掩盖失败。

### 场景 4：失败场景——问题无法复现

记录环境、频率、最后正常版本和所需最小观测点，提供下一次采样方案。不能仅凭一张截图宣布根因或直接修改多个模块。

### 场景 5：不应触发——产品想法尚未定义

用户希望新增一个奖励页，但用户、规则和状态未确认。应进入产品规格流程，不把需求缺失当成代码缺陷调试。
