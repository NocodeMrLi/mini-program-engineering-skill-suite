# 小程序发布治理工作流与触发场景

## 发布证据梯级

| 状态 | 最低证据 | 不能替代 |
| --- | --- | --- |
| `release-ready` | 目标版本验证、安全、配置和回滚门禁通过 | 平台上传 |
| `uploaded` | 平台上传记录、版本号或包标识 | 审核提交 |
| `review-submitted` | 审核提交回执和对应版本 | 审核通过 |
| `review-approved` | 平台审核结果和对应版本 | 正式发布 |
| `released` | 正式环境或平台发布证据 | 用户正式验收 |

## 授权检查

先判断用户动词：检查、核对、准备、评估只允许只读预检；上传、提交审核、发布、推送等动作必须有明确目标和授权。授权只覆盖点名动作，不向后自动扩展。

输出后续行动时，每个行动条目只能包含一个外部动作，并分别标记授权需求；不得合并授权。即使执行顺序连续，也必须把代码推送、平台上传、体验版生成、提交审核、正式发布、云端修改和付费资源创建拆成不同条目。一项得到授权后只执行该项，完成取证并停止；不得把“推送并上传”“上传后提审”或“审核通过后发布”写成一次授权即可连续执行的动作。

## 代表场景

### 场景 1：正常场景——只读发布就绪检查

核对分支、版本、工作区、构建指纹、验证报告、测试开关、安全、权限隐私和回滚。全部门禁通过时只报告 `release-ready`，不上传。

### 场景 2：正常场景——已授权平台上传

用户明确指定版本和上传目标，且预检通过。执行后保存平台回执并标记 `uploaded`；没有审核提交授权时立即停止。

### 场景 3：边界场景——历史记录称已提交审核

历史文档可以说明来路，但若当前平台回执和版本对应关系不可查，只报告“历史记录称已提交”，不能升级为当前审核通过或正式发布。

### 场景 4：失败场景——源码与构建产物不一致

版本号、路由、测试开关或关键标记冲突时判定 `not-ready`，列出重建和复验入口。不得选择更有利的一份证据继续上传。

### 场景 5：失败场景——版本事实源只更新了一部分

`VERSION`、项目元数据、README、CHANGELOG、发布清单、测试断言、构建/导出清单、平台上传备注或体验版/审核版记录中任一关键版本停留在旧值时，判定 `not-ready`。先同步版本事实源并重跑版本一致性检查；不得把“README 已显示新版本”或“GitHub 已推送”当成整条发布链路已升级。

### 场景 6：不应触发——普通本地开发

用户只要求修改一个本地函数且没有发布或交付判断，应进入实现或调试流程，不加载发布治理。

## 阻塞优先级

敏感信息、错误目标版本、关键验证失败和不可回滚变更为硬阻塞；缺少低风险非关键说明可作为残余风险。每个例外都需记录依据、影响和责任边界，不能用“赶时间”删除证据门禁。
