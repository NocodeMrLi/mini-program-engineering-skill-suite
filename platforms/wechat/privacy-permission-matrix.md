# 权限与隐私静态映射

逐项建立“源码 API → 客户端授权/scope → 配置声明 → 平台申报 → 用户拒绝/撤回路径”的证据链。每层状态使用 `confirmed / contradicted / unknown`，不得从相邻层自动推导。

| 能力/目的 | 源码 API 与调用位置 | scope/客户端状态 | 配置声明 | 平台申报 | 用户拒绝路径 | 撤回/重新授权路径 | 证据与结论 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待核对能力 | 仅记录文件与符号，不复制敏感参数 | `confirmed / contradicted / unknown` | 配置文件、字段、版本指纹 | 后台证据、时间、目标版本或 `unknown` | 拒绝后的提示、降级与功能可用性 | 设置入口、撤回后的状态清理与再请求条件 | 各层独立写适用结论 |

## 判定规则

核查覆盖当前交付包全部入口，不能仅看当前修复页面。增加以下版本与主体矩阵，不将代码事实当后台栏位分类依据：

| 目标版本/入口 | 设备权限请求方 | 数据产生/上传/保存 | 接收处理主体与用途 | 官方分类依据/未核 | 告知/附件/后台状态 |
| --- | --- | --- | --- | --- | --- |
| 现网/提审/新候选分别绑定指纹 | 客户端、SDK 或无设备申请 | 实际调用链与数据类别 | 应用/第三方、API/SDK 接入分别记录 | 当前官方链接、日期或 unknown | 完整预览、实际下载附件及版本 |

- 第三方未申请设备权限不等于应用不申请；服务端 API 没有客户端 SDK 也不等于无需披露第三方数据处理。
- 分类证据不明确时保持未核，保留真实权限及处理披露，不确定强删整个服务、不捏造 SDK、不保证审核通过。
- 旧通过版及同源附件保留；新增数据、用途和主体形成新候选增量，旧通过不覆盖新处理，新候选也不能反写为旧已通过内容。
- 主流程告知、文件准备、实际上传、后台填写、提交、通过、生效分列；编辑框截断或旧附件不能证明完整材料。同步时点依当前规则及实际处理开始时间确认，不统一规定提交代码时更新。

- 发现源码 API 只能证明存在调用候选，不能证明用户已授权、配置声明正确或平台申报完成。
- `getSetting`、`openSetting` 或本地 scope 结果只能支持客户端授权层，不能证明平台申报。
- 没有后台当前版本证据时，平台申报必须保持 `unknown`；历史截图不得替代当前状态。
- 用户拒绝和撤回应作为一等流程验证：检查清晰提示、最小功能降级、再次触发条件、缓存/状态清理与退出路径。
- 只读扫描不得回显 AppID、密钥、手机号、用户数据、请求载荷或后台隐私内容。
